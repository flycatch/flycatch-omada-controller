## 3. Entrypoint and health check scripts

- [x] 3.1 Implement `entrypoint.sh` (run under `tini`): chown `data`/`logs`/`work` to the `omada` user, set `OMADA_USER=omada`, seed `data/check-mongo/LAST_MAIN_VERSION.info` if absent so `control.sh` never prompts, run `bin/control.sh start` (which daemonizes the controller via `jsvc` and lets the controller start its own `mongod`), then stay in the foreground by polling the daemon pid and exiting non-zero if it dies. Verify by starting a container and confirming the `jsvc`/Java process and the controller-launched `mongod` are running (`docker exec ... ps`) and the controller UI becomes reachable.
- [x] 3.2 Implement signal handling in `entrypoint.sh` so that `SIGTERM` runs `bin/control.sh stop` (the controller stops itself and its embedded `mongod`; `control.sh` waits up to 30s before killing), completing within a documented stop-timeout window. Verify by running `docker stop -t 60 <container>` and confirming (via logs and a subsequent clean restart) that MongoDB shut down cleanly with no corruption/repair messages on next start.
- [x] 3.3 Configure the entrypoint/Dockerfile so controller and MongoDB logs (`logs/startup.log`, `logs/server.log`, `logs/mongod.log`) are visible via `docker logs` (e.g., tailing log files to stdout/stderr) in addition to being written to the persisted logs volume. Verify by running `docker compose logs` and confirming startup and runtime log lines appear.
- [x] 3.4 Implement `healthcheck.sh` to request `http://127.0.0.1:8088/actuator/linux/check` (port from `manage.http.port`) and return healthy only on HTTP 200 or 503, the same readiness test `control.sh` uses, and wire it into the Dockerfile's `HEALTHCHECK` with a `--start-period` long enough for first-boot initialization (determine an appropriate value by timing a clean first start in task 3.1's verification). Verify by running `docker inspect --format='{{json .State.Health}}'` and observing the transition from `starting`/`unhealthy` to `healthy` once the controller UI is reachable.

## 5. Backup and restore scripts

- [x] 5.2 Implement `scripts/restore.sh`: requires the target container to be stopped, clears/replaces the data volume's contents with the contents of a provided backup archive, and reports success/failure clearly; it SHALL refuse to run (with a clear error) if it cannot confirm the container is stopped. Verify by stopping a controller, running the restore script with a backup produced by 5.1 onto a separate/fresh data volume, starting the container, and confirming the restored site/device configuration is present.
